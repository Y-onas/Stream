# Video player controls

The public player owns its controls inside the video frame. The same custom controls remain visible during authorization and buffering; the video element is created only after authorization supplies its URL. Native controls are disabled from the element's first render. Play/pause, ±10-second skips, the seek bar, volume, settings and fullscreen operate on that existing element and authorized stream URL.

Playback speed supports 0.5×, 0.75×, 1×, 1.25×, 1.5× and 2×. Each new video starts at 1× with sound on. Speed and sound are independent, and preferences survive transport recovery within the same video. Speed changes do not create another playback session or impose a network throttle.

The current delivery service supplies one original file per video. Quality therefore displays only that original's decoded resolution, read from `videoHeight` after metadata loads (or “Original stream” until known). No Auto/adaptive or alternate-resolution options are advertised without corresponding media sources. This change adds no transcoding, caching or backend variants.

Keyboard shortcuts on the player: Space/K play or pause; left/J rewind; right/L forward; M toggle sound; up/down adjust volume; F fullscreen. Escape closes settings and returns focus. Speed choices support arrow/Home/End navigation. Mobile menus scroll within the player when necessary.

Seeking shares the existing 250ms coalescing queue and bounded recovery logic. Timeline dragging and repeated skip taps retain their latest target, preserving Range playback, authorization renewal, progress and qualified-view events.

Opening a video automatically requests playback **from the beginning** once its authorized source exists, without waiting for saved progress, metadata or a second Play click. Existing unfinished progress is read independently and offered as an optional “Continue from …?” Resume button. Ignoring or dismissing it leaves current playback untouched. The suggestion expires 20 seconds after the first actual playing event (or earlier if playback reaches the saved position). Authorization and initial buffering do not consume that window; subsequent buffering/playing events never extend it. A delayed progress response only updates the suggestion; it never seeks or restarts the video, and cannot reopen an expired suggestion. There is one automatic attempt per element/source, so rerenders, focus refreshes and StrictMode effect replays never undo a manual pause. Retry creates a new element and gets a new attempt.

Resume uses the current media element, loaded metadata/seek index and whatever bytes its browser buffer already contains. It seeks directly to the saved time without replacing the source, calling `load()`, creating another playback session or resetting speed/sound. If selected before metadata arrives, the existing transport retains the target until duration is known. This is background preparation of progress and reuse of browser buffering, not a hidden second video download: the current per-session upstream policy permits one active read, and a competing speculative download would impair primary playback. An unbuffered destination still requires normal HTTP Range retrieval; instant access to every saved position is not promised.

Sound remains on. If the browser rejects `play()` with `NotAllowedError`, the player shows an explicit Play fallback; it never silently mutes or changes browser permissions. Source errors use the existing bounded recovery. Early Play intent is retained even if a network error happens before the first frame, while actual pauses still prevent automatic resumption. [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay/) explains when a user interaction is required.

Attaching controls does not replace the media element, reset its source, call `load()`, or rewrite unchanged playback preferences. Preload remains metadata-only; authorization still runs before a media URL is supplied. Known non-members still receive no media element or media URL.

## Original-file delivery

The production Go route fetches a 256 KiB first part before committing success headers (increased from 64 KiB so the first successful response supplies more startup data). Subsequent large ranges use Telegram's supported 1 MiB parts to reduce sequential RPC overhead. Small probe/seek ranges retain the smaller read size. `ReadChunk` aligns each read within one Telegram window and slices the exact HTTP range; growing the first window can reread a bounded prefix once. HTTP writes remain at most 64 KiB with normal backpressure and refreshed write deadlines, independent of the larger Telegram read size. Cancellation and authorization revocation still cancel the same request context. No persistent video cache, parallel speculative fetching or transcoding is introduced.

Each production HTTP request creates a fresh Telegram backend, whose constructor already resolves the document. Its one-use request provider reuses that fresh metadata rather than immediately making the same lookup twice. Further opens resolve again, document replacements are still rejected, and each reader receives an independent metadata copy. The long-lived development CLI retains its per-request metadata refresh. This removes one Telegram lookup from startup without retaining media bytes or sharing request state.

A deterministic 4 MiB fixture takes five Telegram part calls instead of sixteen 256 KiB calls, while the first write stays 64 KiB. This demonstrates reduced request count, not a live throughput or time-to-first-frame guarantee. Protocol reference: [Telegram file downloads](https://core.telegram.org/api/files#downloading-files).

Production requests now borrow reusable Telegram connection pools scoped to the authenticated client, while keeping request-private metadata and readers. Finishing a request leaves the transport available for later videos and viewers; reconnect/shutdown closes the owner. This retains no video bytes. See [Telegram connection reuse](telegram-connection-reuse.md) for configuration, cancellation and lifecycle details.

Larger parts cannot reduce the source bitrate or remove Telegram/network limits. For example, a 1 GB original lasting eight minutes averages approximately 16.7 Mbps before overhead. At 2× playback it needs approximately twice that delivery rate. The selected policy retains original quality and improves delivery only; slower connections may still buffer. No fake lower-resolution choices are shown.

Verification includes unit tests for automatic startup, browser-policy rejection, seek coalescing, transport recovery and independent media preferences; production builds; Go tests for exact bytes, small initial writes, larger subsequent parts and cancellation; and browser checks against the actual built frontend with an isolated synthetic MP4 fixture. Separate authorization/media delays verify that custom controls exist before a media URL and that a video-card click starts playback without another Play click. Desktop, 390px and 320px layouts were inspected. Live Telegram/VIP playback was not exercised as part of these UI checks.
